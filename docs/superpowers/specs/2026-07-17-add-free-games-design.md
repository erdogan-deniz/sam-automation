# Дизайн: авто-добавление бесплатных игр/приложений Steam (v1)

- **Дата:** 2026-07-17
- **Статус:** согласован владельцем, готов к writing-plans
- **Ветка:** `feature/add-free-games`

## Цель

Один запуск процесса → программа сама добавляет в библиотеку аккаунта всё
бесплатное, чего там ещё нет (F2P-игры, бесплатные не-игровые app, демо).
Резюмируемость и честный отчёт — обязательны (инвариант проекта).

## Зафиксированные решения владельца

- **Источник:** весь каталог Steam (авто-обнаружение), не ручной список.
- **Тип контента:** всё — F2P-игры, бесплатные app, демо; промо/free-weekend —
  по возможности (не обещаем).
- **Порядок:** всё подряд, без приоритизации.
- **Discovery-стратегия:** витрина free (`store search maxprice=free`) +
  демо отдельной под-фазой. (Выбрано из 3 вариантов; полный
  `GetAppList ∩ appdetails` отклонён — часы/дни rate-limit, ненадёжный Store
  API, уже терявший игры в v1.1.1.)
- **Дефолт запуска:** dry-run. Реальное добавление — только по явному `--add`.

## Жёсткие ограничения Steam (учтены)

- **Потолок free-лицензий аккаунта** ~1000–2000 пакетов — это стена, не мягкий
  лимит. «Весь каталог» физически не влезет → нужен детект упора + честная
  остановка. Следствие: discovery должен *набрать достаточно кандидатов до
  упора*, а не перечислять весь каталог (~200k appid).
- **`request_free_license` жёстко rate-limit'ится** → батчи + backoff.
- **Глобального API-списка free-weekend/промо пакетов нет** (только витрина);
  демо перечислимы (`type=demo`, `is_free`), промо — оппортунистически.
- **Урок [[project_scan_catalog_reverted]]:** Store API ненадёжен как источник
  *терминальных* решений о своих играх (терял игры → откат v1.1.1). Здесь роль
  иная — *обнаружение кандидатов*, где потеря отдельного не критична (потолок
  всё равно стена, полноту не обещаем). Тот же инструмент в безопасной роли.

## Архитектурное решение: живой CM-клиент

`request_free_license` нужно звать на **живом залогиненном** `SteamClient`.
Сейчас весь 6-слойный логин (JWT→RSA→2FA) заперт внутри
`read_steam_cm_app_ids`, которая в `finally` отключается и наружу клиент не
отдаёт.

**Решение (Подход C):** извлечь логин в контекст-менеджер
`cm_session()` в `app/auth`, возвращающий залогиненный живой `SteamClient` и
гарантирующий `disconnect()` в `__exit__` (формализует существующий
`try/finally`). `read_steam_cm_app_ids` переписывается поверх него тонким
потребителем. `add_free` использует тот же `cm_session()`.

- Поведение-сохраняющий рефактор: существующие CM/scan-тесты — regression-сеть.
- Отклонён Подход A (дублировать логин): две копии хрупкого auth → дрейф,
  против DRY и памяти проекта (auth стоил серии 6-слойных багов).

## Структура файлов

- `scripts/library/add_free.py` — тонкий CLI-скрипт (как `scan.py`), НЕ
  типизируется mypy. Разбор аргументов + вызов оркестратора в `app/`.
- `app/free_games/` — логика (типизируется mypy):
  - `discovery.py` — витрина free + демо-подфаза → список кандидатов.
  - `licenses.py` — батчи `request_free_license`, cap-детект, backoff.
  - `state.py` — resume-файлы (candidates/added/refused/error).
  - `report.py` — сбор честного итога (toast + telegram).
  - `orchestrate.py` (или `__init__`) — склейка фаз, main-логика.
- `app/auth/…` — новый `cm_session()` контекст-менеджер.

## Фаза discover

Пишет `data/games/ids/free/candidates.txt`.

1. **Витрина:** пагинация `store search maxprice=free` (переиспользовать
   429-backoff-паттерн из `app/steam/steam_api.py::_api_get`), парсинг appid из
   ответа. Набираем кандидатов с запасом относительно потолка аккаунта.
2. **Демо-подфаза:** отдельный запрос `type=demo` / `is_free`. Пропускается по
   `--no-demos`. (По умолчанию включена — зафиксировано «включая демо».
   Trade-off: демо съедают ограниченный потолок и истекают — отсюда флаг
   отключения.)
3. **Вычитание owned:** из `client.licenses` живого CM (authoritative для
   аккаунта) → `expand_packages_to_apps` → owned appids. Кандидаты =
   `discovered − owned − added − refused`.

Discovery устойчив к сбою отдельного источника: падение витрины/демо/CM
логируется WARNING, не роняет прогон; частичный список кандидатов допустим
(полнота не гарантируется).

## Фаза add (только по `--add`)

1. Читаем `candidates.txt` минус `added`/`refused` (resume).
2. Батчи по ~50 appid на вызов `request_free_license`. Между батчами — пауза.
3. Ответ разбираем по `eresult` + `granted_appids`:
   - granted → в `added.txt` (`_append_id`).
   - CM отказал (не-cap причина) → `refused.txt` (терминально), причина в лог.
   - транзиентная ошибка → `error.txt` (восстановим `--retry-errors`).
4. `--limit N` — потолок числа добавлений за прогон (безопасность/тест).

### Cap-детект + честная остановка (инвариант)

Сигнал потолка лицензий (`EResult.LimitExceeded` либо серия `granted=[]` при
`eresult=OK` — **точный сигнал уточняется на integration-прогоне**) →
немедленный стоп. Массово `refused` НЕ пишем. Честный тост:
«Добавлено N, дальше стена (потолок лицензий)».

Rate-limit (`EResult.RateLimitExceeded` / HTTP 429) → экспоненциальный backoff
(база ~2с, cap ~60с, ограниченное число попыток), НЕ стоп.

## Resume-состояние (паттерн id-файлов проекта)

Каталог `data/games/ids/free/` (в `.gitignore`, как прочий `data/`):

| Файл | Смысл | На resume |
|---|---|---|
| `candidates.txt` | обнаруженные кандидаты | вход фазы add |
| `added.txt` | успешно добавленные (granted) | skip |
| `refused.txt` | CM отказал — **терминально** | skip |
| `error.txt` | транзиент | skip, восстановим `--retry-errors` |

Все записи — через `_atomic_write_text` / `_append_id` (сортировка, атомарность).
Причины отказа — в лог-файл (id-файлы хранят только int).

## CLI

| Флаг | Действие |
|---|---|
| *(без флагов)* | dry-run: discover + отчёт «найдено N кандидатов», НЕ добавляет |
| `--add` | реально добавлять лицензии |
| `--list` | показать текущих кандидатов из `candidates.txt` |
| `--reset` | сбросить состояние (candidates/added/refused/error) |
| `--retry-errors` | повторить `error.txt` (НЕ `refused` — терминален) |
| `--limit N` | потолок числа добавлений за прогон |
| `--no-demos` | пропустить демо-подфазу |

## Честный отчёт

`app/notify.py::toast()` + `send_telegram()`. Итог: «добавлено X / отказано Y /
упор в стену / прервано». Никогда «добавлено всё» при упоре в лимит, rate-limit
или Ctrl+C.

## Run-lock

Фича не спавнит `SAM.Game.exe` → run-lock не берём (как `scan.py`). НО
`request_free_license` дёргает Steam-сессию аккаунта: **проверить на
integration**, не конфликтует ли с параллельным `farm`/`boost`
([[project_farm_boost_conflict]]). Если конфликт реален — добавить лёгкое
предупреждение либо участие в общем локе. В v1 — минимум предупреждение в доке.

## Тестирование (TDD)

Юнит на моках (`tests/unit`, гоняется в CI):

- парсер витрины free (фикстура ответа store search);
- дедуп-вычитание owned из кандидатов;
- батчинг `request_free_license` (fake client);
- cap-детект (fake `EResult.LimitExceeded` / серия пустых granted);
- backoff на rate-limit (fake 429 / `RateLimitExceeded`);
- resume-слияние файлов (added/refused/error + skip-логика);
- честность отчёта (упор в стену / rate-limit / Ctrl+C ≠ «добавлено всё»);
- `cm_session` на фейковом клиенте без сети (вход по факту, disconnect в
  `__exit__`);
- регрессия: `read_steam_cm_app_ids` поверх `cm_session` — существующие тесты
  зелёные.

Интеграция (реальный CM, `request_free_license` на живом аккаунте) — вне CI,
ручной прогон владельцем. Именно она уточняет точный сигнал cap.

## Не-цели v1 (YAGNI)

- Web `addfreelicense` по subid (HTML-скрейп subid хрупкий) — отдельный будущий
  инкремент.
- Промо/free-weekend пакеты (глобального списка нет).
- Гарантия 100% полноты каталога (потолок аккаунта + неполнота витрины — честно
  сообщаем в отчёте, не претендуем на «всё»).
